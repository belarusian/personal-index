# QA-25: Zero-cap eviction slicing gotcha — `list[-0:]` keeps everything (5 sites)

Status: OPEN
Priority: medium
Component: personal_index/versioning.py, content_diff/snapshot.py, performance_monitor.py, content_monitor/alert.py, notifications.py
Filed: Cycle 194
Issue: #1237
Deep test: tests/deep/test_zero_cap_eviction_sweep_adversarial.py

## Summary

Five retention/eviction sites cap a list with the idiom

    if len(lst) > cap:
        lst = lst[-cap:]

When `cap == 0`, Python evaluates `lst[-0:]` as `lst[0:]` — the **full list** —
so a zero cap silently keeps **every** entry instead of none. The cap is
ignored rather than enforced. This is the same slicing-gotcha family as the
negative-slice "top N" leaks (QA-15 `content_summarizer.summarize`, QA-16
`content_search.SearchIndex.search`), but for the eviction-cap idiom.

Whole-codebase sweep (`grep '[-self.<cap>:]'` over `personal_index/`) found
exactly these five public sites, all unguarded against `cap == 0`:

| # | Site | Method | Cap field |
|---|------|--------|-----------|
| 1 | personal_index/versioning.py:93 | `VersionTracker.record_version` | `self._max_versions` |
| 2 | personal_index/content_diff/snapshot.py:83 | `SnapshotManager.create_snapshot` | `self.max_snapshots` |
| 3 | personal_index/performance_monitor.py:85 | `PerformanceMonitor.record` | `self._window_size` |
| 4 | personal_index/content_monitor/alert.py:84 | `AlertManager.add_alert` | `self.max_alerts` |
| 5 | personal_index/notifications.py:168 | `InMemoryHandler.handle` | `self.max_size` |

Each is a public entry point (constructor kwarg + public method), so a caller
can reach the bug without touching private state.

## Consequence

- A caller that constructs any of these with a zero cap (e.g.
  `VersionTracker(max_versions=0)`, `PerformanceMonitor(window_size=0)`)
  expecting "keep nothing" instead gets unbounded growth: every recorded
  entry is retained forever.
- The cap contract is silently violated at the boundary value 0; positive
  caps work correctly (see armor tests).

## Repro

    python3 -c "
    from personal_index.versioning import VersionTracker
    from personal_index.content_diff.snapshot import SnapshotManager
    from personal_index.performance_monitor import PerformanceMonitor
    from personal_index.content_monitor.alert import AlertManager, AlertLevel
    from personal_index.notifications import InMemoryHandler, Notification

    t = VersionTracker(max_versions=0)
    for i in range(3): t.record_version('u', f'c{i}')
    print('versioning cap0:', t.get_change_count('u'))   # expect 0, got 3

    sm = SnapshotManager(max_snapshots=0)
    for i in range(3): sm.create_snapshot({'id': 'x', 'v': i})
    print('snapshot cap0:', len(sm.get_snapshots('x')))  # expect 0, got 3

    pm = PerformanceMonitor(window_size=0)
    for i in range(3): pm.record('m', float(i))
    print('perf cap0:', len(pm.get_recent_samples('m', count=100)))  # expect 0, got 3

    am = AlertManager(max_alerts=0)
    for i in range(3): am.add_alert(AlertLevel.INFO, f'm{i}', 's')
    print('alert cap0:', len(am.alerts))                 # expect 0, got 3

    h = InMemoryHandler(max_size=0)
    for i in range(3): h.handle(Notification(title=f't{i}'))
    print('notif cap0:', len(h._notifications))          # expect 0, got 3
    "

Actual output:

    versioning cap0: 3
    snapshot cap0: 3
    perf cap0: 3
    alert cap0: 3
    notif cap0: 3

## Expected per docs

Per each site's documented retention contract (e.g. versioning "Enforce max
versions", snapshot "only the last ``max_snapshots`` are retained",
performance_monitor window, alert "Maximum number of alerts to retain",
InMemoryHandler `max_size`), a cap of 0 must retain zero entries. The fix is a
`cap <= 0` guard at each site (treat 0/negative as "keep nothing", or clamp to
a sane minimum) so `list[-cap:]` is never evaluated with `cap == 0`.

## Pinned

`tests/deep/test_zero_cap_eviction_sweep_adversarial.py` pins all five sites as
`xfail-strict` (each currently FAILS, documenting the expected zero-retention
contract) plus five positive-cap armor tests that currently PASS. When the
implementer adds the guard, the five xfail pins flip to XPASS -> strict
failure forces re-verification and closure of this ticket.
