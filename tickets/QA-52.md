# QA-52: Scheduler.get_due_schedules crashes (TypeError) on naive stored datetimes

- **Component:** `personal_index/scheduler.py` (`ScheduleStore._load` + `Scheduler.get_due_schedules`)
- **Status:** CLOSED (validator close, cycle 325 @ main e7e238a; deep pin tests/deep/test_scheduler_adversarial.py::TestGetDueSchedules::test_naive_stored_datetime_does_not_crash_get_due passed; gh #1636 already closed)
- **Issue:** #1636
- **Deep test:** `tests/deep/test_scheduler_adversarial.py::TestGetDueSchedules::test_naive_stored_datetime_does_not_crash_get_due` (xfail-strict pin)

## Symptom
`ScheduleStore._load` parses `last_run`/`next_run` with `datetime.fromisoformat(...)`
and accepts an offset-NAIVE ISO string (e.g. `"2026-01-01T00:00:00"`). The public
`Scheduler.get_due_schedules()` then compares that naive `entry.next_run` against
`datetime.now(timezone.utc)` (an offset-AWARE datetime). Comparing a naive datetime
to an aware one raises `TypeError`, so a store file written with naive timestamps
makes the entire `get_due_schedules()` call crash.

The module's own `_save`/`add_schedule` paths always emit aware (UTC) datetimes, so
the crash is only reachable when the store file is produced by an external writer or
an older/hand-edited file — but `_load` explicitly tolerates such input (it does not
reject or normalize naive timestamps), so the public API must be robust to it.

## Exact repro
Run this one-liner from the repo root:

    python3 -c "import json,tempfile,os; from personal_index.scheduler import ScheduleStore, Scheduler;
    class S: pass;
    d=tempfile.mkdtemp(); p=os.path.join(d,'naive.json');
    open(p,'w').write(json.dumps({'j':{'config':{'interval_hours':24,'enabled':True,'seed_urls':[],'max_pages_per_run':50,'crawl_depth':2,'delay':1.0},'run_count':0,'total_pages_indexed':0,'last_run':'2026-01-01T00:00:00','next_run':'2026-01-01T00:00:00'}}));
    store=ScheduleStore(path=p);
    sch=Scheduler(interest_store=S(),search_index=S(),schedule_store=store);
    sch.get_due_schedules()"

## Expected per docs
`ScheduleStore._load` is documented as defensive (it already swallows
`json.JSONDecodeError/KeyError/TypeError/ValueError` and returns an empty store on
malformed input). A loaded entry must therefore be usable by the public
`get_due_schedules()` without raising. The fix is to normalize naive timestamps to
UTC in `_load` (e.g. `if last_run.tzinfo is None: last_run = last_run.replace(tzinfo=timezone.utc)`),
so the aware/naive comparison in `get_due_schedules` is always valid.
