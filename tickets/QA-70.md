# QA-70: TypeHandler.can_handle always returns False (supported_types left None)

- **Status:** CLOSED (validator cycle 345 @ main be2e5dc; re-ran pinning deep tests tests/deep/test_content_router_adversarial.py green + fresh adversarial TypeHandler.can_handle({type:weird})/({}) -> True, supported_types=[*]; issue #1736 already CLOSED by implementer fix PR)
- **Component:**
  * `personal_index/content_router/handler.py` (`TypeHandler.__post_init__`, lines ~60-62)
- **Kind:** contract violation (base-class docstring vs code — `can_handle` dead)
- **Issue:** #1736
- **Deep test:** `tests/deep/test_content_router_adversarial.py` (2 xfail-strict pins: `test_typehandler_can_handle_typed_content`, `test_typehandler_can_handle_unknown_type`)

## Symptom

`ContentHandler` is a dataclass whose `__post_init__` normalizes a missing
`supported_types` to `["*"]`:

    def __post_init__(self) -> None:
        if self.supported_types is None:
            self.supported_types = ["*"]

and whose `can_handle` docstring promises:

    True if handler supports this content type.

`TypeHandler` (a concrete handler whose docstring says it "processes content
based on type") overrides `__post_init__` to set `name` but does NOT call
`super().__post_init__()`:

    def __post_init__(self) -> None:
        self.name = "type_handler"

So `TypeHandler.supported_types` stays `None`, and the base `can_handle`
returns `False` for EVERY input:

    def can_handle(self, content):
        content_type = content.get("type", "unknown")
        if self.supported_types is None:
            return False
        return "*" in self.supported_types or content_type in self.supported_types

This is self-contradictory: `TypeHandler.handle()` happily accepts and
processes ANY content (it never rejects), yet `TypeHandler.can_handle()`
reports that it can handle NOTHING. Its sibling `PassThroughHandler` (which
also overrides `__post_init__`) explicitly sets `supported_types = ["*"]` and
therefore `can_handle` returns `True` for any type — the two concrete handlers
behave inconsistently for the same base contract.

## Exact repro

    python3 -c "
    from personal_index.content_router.handler import TypeHandler, PassThroughHandler
    t = TypeHandler()
    print('TypeHandler.supported_types =', t.supported_types)
    print('TypeHandler.can_handle(article) =', t.can_handle({'type': 'article'}))
    print('PassThrough.can_handle(article) =', PassThroughHandler().can_handle({'type': 'article'}))
    "

## Traceback

No exception is raised; the defect is a wrong return value:

    TypeHandler.supported_types = None
    TypeHandler.can_handle(article) = False   <- expected True
    PassThrough.can_handle(article) = True    <- sibling, correct

## Expected per docs

`can_handle` must return `True` for content the handler supports. `TypeHandler`
processes content of any type (its `handle` never rejects), so `can_handle`
should return `True` for typed content and for unknown-type content, consistent
with the base docstring and with `PassThroughHandler`. The fix is to call
`super().__post_init__()` in `TypeHandler.__post_init__` (or set
`self.supported_types = ["*"]`), so `supported_types` is normalized to `["*"]`
instead of left `None`.

## Asymmetry (same base contract, only the subclass differs)

    PassThroughHandler().can_handle(any) -> True  (correct)
    TypeHandler().can_handle(any)        -> False (defect)
