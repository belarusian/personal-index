## Symptom

Cycle 338 re-ran the naive-vs-aware datetime seam CLASS SWEEP
(`grep -rn fromisoformat personal_index/`) and traced every non-pycache call
site to its public entry point and its downstream comparison/subtraction/sort
context. Three NEW, previously-unfiled seam members were found. In each, the
per-item parse is guarded by `except (ValueError, TypeError)` (or is
parse-only), but a DOWNSTREAM sort/min of the parsed results sits OUTSIDE that
guard, so a mixed naive+aware list passes every per-item parse and only fails
at the sort step, raising an uncaught `TypeError` out of a public entry point:

1. `content_feed.py:107` — `FeedGenerator.add_item` sorts `self.items` by
   `i.published`. A naive `published` (produced by `FeedItem.from_dict` from a
   naive ISO string) mixed with an aware `published` (the `__post_init__`
   default `datetime.now(timezone.utc)`) raises `TypeError` at the sort.

2. `content_timeline/timeline.py:37` (`add_event`) and `:67` (`add_entry`) —
   sort by `timestamp`. A naive timestamp (produced by
   `TimelineEvent.from_dict` / `TimelineEntry.from_dict` from a naive ISO
   string) mixed with an aware timestamp (the default) raises `TypeError`.

3. `content_backup/backup_store.py:95-97` (`list_backups`) and `:126`
   (`_evict_oldest`) — sort/min by `timestamp`. A naive timestamp (produced by
   `import_from_file` from a naive ISO string) mixed with an aware timestamp
   (`add_backup` default) raises `TypeError`.

This is the same naive-vs-aware datetime seam class as:
  * QA-62 (content_archive.archive_old — VERIFIED, fixed in #1715)
  * QA-63 (sitemap.get_recent_entries + progress.elapsed_seconds — OPEN)
  * QA-64 (auth/api_keys.validate_key — OPEN)
  * QA-65 (search_facets range filters — OPEN)
  * QA-66 (dashboard/aggregator._compute_pages_per_day — OPEN)

## Expected per docs

Each site sorts (or takes `min` of) datetimes that can be either naive or
aware. A naive ISO string is a valid input and parses successfully to a naive
datetime. The sort should compare a naive datetime against an aware one the
same way it compares two aware values: normalize a naive datetime to
UTC-aware (e.g. `dt.replace(tzinfo=timezone.utc)` when `dt.tzinfo is None`)
before sorting — exactly the reference fix in `content_scoring._score_recency`
(content_scoring.py:267-268). After the fix, a mixed naive/aware list should
sort without raising.

## Asymmetry (same items, only tz-awareness differs)

    mixed naive+aware -> RAISES TypeError (defect)
    all aware         -> sorts (correct)
    all naive         -> sorts (correct)
