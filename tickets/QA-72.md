## Symptom

`format_tree` documents `max_lines` as a hard cap on output lines (docstring
line 283: "max_lines: hard cap on output lines"; docs/cycle-signals.md line 64:
"hard-caps output at `max_lines`"). The terminal slice clamps only the TOP,
with no floor:

    return "\n".join(lines[:max_lines])   # line 308

`lines[:max_lines]` caps the upper bound for a positive `max_lines`, but there
is no `max(0, max_lines)` lower bound. A NEGATIVE `max_lines` is out-of-range
and Python's negative-slice semantics return ALL-BUT-LAST `abs(max_lines)`
lines instead of an empty output. `max_lines=0` correctly returns `""` (the
floor that DOES exist), so the cap has a floor at 0 but not below it — the
one-sided-guard (cap-without-floor) defect class already filed at QA-15/QA-16/
QA-31/QA-71 (a `min(x, CAP)` / `[:cap]` without `max(0, x)` passes a positive-N
check but leaks on a negative N).

The defect is USER-REACHABLE: the CLI exposes it as `--lines` (line 679,
`type=int`, no lower bound), so `cycle_signals.py <codemap> --format tree
--lines -1` returns all-but-last lines instead of an empty/zero-cap output.

## Exact repro

    python3 -c "
    from personal_index.cycle_signals import format_tree
    tree = {'name':'root','signals':[],'stats':{'modules':10,'lines':100,'functions':10},
            'children': {f'pkg{i:02d}': {'name':f'pkg{i:02d}','signals':['S2'],
            'stats':{'modules':1,'lines':10,'functions':1},'children':{}} for i in range(10)}}
    print('max_lines=0  ->', repr(format_tree(tree, max_depth=1, max_lines=0)))
    print('max_lines=-1 ->', len(format_tree(tree, max_depth=1, max_lines=-1).splitlines()), 'lines (leak)')
    print('max_lines=-2 ->', len(format_tree(tree, max_depth=1, max_lines=-2).splitlines()), 'lines (leak)')
    "

## Traceback / observed output

    max_lines=0  -> ''
    max_lines=-1 -> 9 lines (leak)
    max_lines=-2 -> 8 lines (leak)

(10 flagged packages render 10 lines; -1 yields 9 = all-but-last, -2 yields 8.)

## Expected per docs

`max_lines` is a hard cap; a negative value is out-of-range and must clamp to
0 (empty output, identical to `max_lines=0`), matching every sibling top-N /
truncate site in the codebase (content_digest.generate `max(0, ...)`,
formatter `max(0, ...)`, index.search / search_index.search /
content_scoring.rank_items / content_search.get_suggestions /
progress.list_completed / content_recommender / keyword_extractor /
search_suggestions / tfidf / content_categorizer.top_n / content_export_csv
all guard `<= 0`). The fix is to add the missing floor at the terminal slice:
`return "\n".join(lines[:max(0, max_lines)])`.

## Deep test

`tests/deep/test_cycle_signals_negslice_adversarial.py` pins the defect with
two `xfail(strict=True)` tests (they XFAIL on current main, proving the
defect; they will XPASS->RED on the fix branch until the implementer adds the
floor, at which point the validator flips them to hard passes). The same file
armor-pins the GUARDED behaviors the module already delivers correctly
(positive max_lines hard cap, zero max_lines empty, the exact negative-slice
leak signature -1 -> full-1 / -2 -> full-2, a no-exceed-full property, and one
end-to-end CLI run through `python -m personal_index.cycle_signals --format
tree --lines`).
