# QA-18: ContentPinner.pin leaves item pinned in-memory on non-serializable metadata

- Status: IMPLEMENTED #1273@1fa08e3
- Component: `personal_index/content_pin.py`
- Issue: #1198

## Symptom

`pin` mutates `self._pinned[item_id]` before calling `_save`. The docstring
promises: "Returns False if the pin could not be persisted (e.g. a disk I/O
error in `_save`); on failure the in-memory state is rolled back so the item
is not left pinned."

The rollback is only wired to `except OSError`. If `_save` raises a
`TypeError` (e.g. metadata contains a non-JSON-serializable value such as a
set), the exception propagates out of `pin` AND the in-memory state is left
with the item pinned. The caller sees an unhandled exception, and the pinner
is now inconsistent with its persisted state (the item is "pinned" in memory
but never written to disk).

## Repro

    python3 -c "import tempfile,os; from personal_index.content_pin import ContentPinner; d=tempfile.mkdtemp(); p=ContentPinner(storage_path=os.path.join(d,'ns.json')); p.pin('good'); p.pin('bad', metadata={'a':{1,2,3}})"

Expected per docs: `pin` returns `False`, the item is rolled back (not left
pinned), and no exception escapes. Actual: `TypeError: Object of type set is
not JSON serializable` propagates, and `p.is_pinned('bad')` is `True`
afterwards (in-memory state not rolled back).

Traceback:

    File ".../personal_index/content_pin.py", in _save
        json.dump(data, f, indent=2)
    TypeError: Object of type set is not JSON serializable

## Deep test

`tests/deep/test_content_pin_adversarial.py::test_pin_non_serializable_metadata_rolls_back`
is xfail-strict with reason referencing QA-18.

## Notes

The fix is to broaden the rollback catch in `pin` (and `unpin`) to cover the
serialization failure mode, or to validate metadata serializability before
mutating state. Validator does not fix; this is a QA ticket for the
implementer.
