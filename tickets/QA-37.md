# QA-37: keyword_extractor.extract(limit=-1) leaks Python negative-slice semantics — returns all-but-last keywords instead of []

## Symptom
`KeywordExtractor.extract(text, limit)` (personal_index/keyword_extractor.py:38-78)
computes `cap = self.max_keywords if limit is None else limit` (line 77) and
returns `keywords[: cap]` (line 78) with NO floor on `limit`. A NEGATIVE
`limit` (out-of-range — the same class as QA-1/15/16/27/35) leaks Python
negative-slice semantics: `keywords[:-1]` returns ALL keywords EXCEPT THE LAST
ONE, instead of an empty list. `limit=0` correctly returns `[]`, so the guard
is missing only for negative values.

This is the negative-slice "top N" defect class (QA-1/2/3/15/16/27/31/35).
The whole-codebase sweep in cycle 220 found that nearly every other "top N"
site is now guarded (`if N <= 0: return []` or `max(0, N)` floors) — including
the sibling `extract_top_n` (QA-1, CLOSED/fixed) and `extract_phrases` — but
`extract(limit=...)` was missed.

Repro (exact):

    python3 -c "
    from personal_index.keyword_extractor import KeywordExtractor
    ke = KeywordExtractor()
    text = 'python python java java java rust go go go go c c c c c c c c c c'
    print([k.text for k in ke.extract(text, limit=None)])  # ['java', 'python', 'rust']
    print([k.text for k in ke.extract(text, limit=0)])     # []
    print([k.text for k in ke.extract(text, limit=-1)])    # ['java', 'python']  (== keywords[:-1], NOT [])
    print(ke.extract_top_n(text, -1))                      # []  (sibling IS guarded)
    "

Traceback (from the deep test, xfail-strict pin):

    tests/deep/test_keyword_extractor_adversarial.py::test_extract_limit_negative_returns_empty
        assert extractor.extract("python python java java java rust go go go go c c c c c c c c c c", limit=-1) == []
    E   AssertionError: extract(limit=-1) = ['java', 'python'] (== keywords[:-1]) violates the documented empty-list contract (QA-37)

## Why it is a real contract violation
- `extract` docstring: "limit: Optional per-call cap on the number of keywords
  returned." A cap of -1 is out-of-range; the documented/observed contract for
  an out-of-range cap is an empty list (as `limit=0` already delivers, and as
  every sibling method delivers).
- The SIBLING methods in the SAME class are all guarded against negative N:
  `extract_top_n` -> `if n <= 0: return []` (line 100-101, fixed in QA-1);
  `extract_phrases` -> `if n <= 0: return []`. `extract` is the ONLY unguarded
  "top N" entry point left in the class — a strong defect signal (same pattern
  as QA-35's unguarded `suggest`).
- The leak is data-dependent and silent: `extract(limit=-1)` returns a
  non-empty, plausible-looking list (all-but-last), so a caller passing a
  negative cap gets wrong results rather than an obvious empty result.

## Expected per docs
- `extract(text, limit=N)` returns `[]` for `N <= 0` (identical to `N=0`),
  matching `extract_top_n` / `extract_phrases` and the rest of the guarded
  "top N" class.

## Fix (implementer)
In `extract`, guard the cap before slicing (line 77-78):

    if limit is not None and limit <= 0:
        return []
    cap = self.max_keywords if limit is None else limit
    return keywords[: cap]

This makes the xfail-strict pin in
`tests/deep/test_keyword_extractor_adversarial.py::test_extract_limit_negative_returns_empty`
XPASS -> the validator removes the marker and re-verifies to close QA-37.
