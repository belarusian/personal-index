# QA-58: ScheduleStore._load wipes the ENTIRE store when ONE entry has a "Z"-suffix (unparseable) ISO timestamp

- **Component:** `personal_index/scheduler.py` (`ScheduleStore._load`, lines ~54-92)
- **Status:** CLAIMED 2026-09-21
- **Issue:** #1690
- **Deep test:** `tests/deep/test_scheduler_zsuffix_adversarial.py::TestZSuffixDataLoss::test_one_z_entry_does_not_wipe_valid_siblings` (version-conditional xfail-strict: active on Python < 3.11 where the defect is real; no-op on >= 3.11 where fromisoformat accepts "Z" and the test passes)
- **Related:** QA-52 (issue #1636) — the naive-datetime fix this probes the neighborhood of; QA-52 hardened the offset-less case but not the unparseable-timestamp case

## Symptom
`ScheduleStore._load` wraps the ENTIRE per-entry parse loop in one
`try/except (json.JSONDecodeError, KeyError, TypeError, ValueError)` whose
`except` body is `self._entries = {}`. On Python 3.10,
`datetime.fromisoformat` does NOT accept the ISO-8601 "Z" suffix (support
landed in 3.11). So a store file in which even ONE entry has a "Z"-suffixed
`last_run` or `next_run` (e.g. written by an external tool, a hand-edited
file, or a newer Python that emits "Z") raises `ValueError` inside the loop;
the `except` fires and wipes EVERY entry — including perfectly valid siblings.

This violates the defensive contract `_load` is documented to honor (the
module's own defensive-load behavior, and the QA-52 fix's stated goal of
tolerating externally-produced store files): a single malformed entry should
be skipped, not destroy the whole store.

The module's own `_save` emits `+00:00` (not "Z"), so a self round-trip is
safe; the data loss is reachable only via externally-produced store files —
exactly the defensive case `_load` is meant to tolerate.

**Version note:** the defect is real on Python < 3.11 (where
`datetime.fromisoformat` rejects the "Z" suffix). On Python >= 3.11
`fromisoformat` accepts "Z", so the store loads the entry fine and the
defect is absent there. The deep pin is version-conditional for this reason.

## Exact repro
Run from the repo root:

    python3 -c "
    import json, tempfile, os
    from personal_index.scheduler import ScheduleStore
    cfg = {'interval_hours':24,'enabled':True,'seed_urls':[],'max_pages_per_run':50,'crawl_depth':2,'delay':1.0}
    def e(lr,nr): return {'config':cfg,'run_count':0,'total_pages_indexed':0,'last_run':lr,'next_run':nr}
    d = tempfile.mkdtemp(); p = os.path.join(d,'s.json')
    open(p,'w').write(json.dumps({'good':e('2026-01-01T00:00:00+00:00','2026-01-01T00:00:00+00:00'),'bad':e('2026-01-01T00:00:00Z','2026-01-01T00:00:00Z')}))
    s = ScheduleStore(path=p)
    print('entries after load:', list(s._entries.keys()))
    "

## Traceback (root cause)

    -> caught by `except (..., ValueError): self._entries = {}`
    -> the valid 'good' entry is also lost.

## Expected per docs
`_load` is defensive: a malformed entry should be skipped (or the whole file
treated as empty only when the file itself is malformed), not used to wipe
valid sibling entries. The valid "good" entry must survive a load in which a
sibling entry carries an unparseable timestamp.

## Minimal additive fix (for the implementer)
Parse each entry's timestamps inside a per-entry `try/except ValueError`
that skips (or normalizes) the offending entry, rather than letting a single
`ValueError` fall through to the whole-loop `except` that resets
`self._entries = {}`.
