## Symptom

`SearchIndex.search(query, filters=...)` accepts a `filters` dict whose values
may be a `$gte`/`$lte` comparison (docs/content-search.md, `_matches_filters`
section: "a dict value supports `$gte` / `$lte` (skipped when the item value
is `None`)"). The code only guards the `None` case:

    if "$gte" in value and item_value is not None and item_value < value["$gte"]:
        return False
    if "$lte" in value and item_value is not None and item_value > value["$lte"]:
        return False

When the item value is a NON-None value whose type is incompatible with the
filter value (e.g. a `str` item value vs an `int` `$gte`), the order
comparison `item_value < value["$gte"]` raises `TypeError`, which propagates
out of the public `search()` call. The docs promise a filter contract (a value
is kept or dropped) but the code crashes instead of deciding. The exact-match
(`!=`) and list/set (`in` / set-intersection) branches are safe under the same
type mismatch because they never order-compare.

The defect is USER-REACHABLE: `search()` is the public entry point and
`filters` is a documented parameter; any caller that filters on a field whose
stored value is not uniformly comparable to the filter value (a mixed-type
field, e.g. some items store a string, others an int) gets an uncaught
`TypeError` rather than a result.

## Exact repro

    python3 -c "
    from personal_index.content_search import SearchIndex
    idx = SearchIndex()
    idx.add_items([
        {'id':'a','content':'alpha one','priority':'high'},
        {'id':'b','content':'beta one','priority':5},
    ])
    out = idx.search('one', filters={'priority': {'\$gte': 3}})
    print(out)
    "

## Expected per docs

`search()` must not raise on a legal `filters` input; it must return the
correctly filtered page. A non-None item value that cannot be ordered against
the filter value should be treated as NOT satisfying the comparison (the item
is dropped from the `$gte`/`$lte` result), consistent with the documented
"skipped when the item value is `None`" guard — the guard should extend to
"skipped (treated as non-matching) when the item value is not comparable to
the filter value". A minimal fix wraps the comparison in a
`try/except TypeError` (or a `type(item_value) is type(value[...])` /
`isinstance` comparability check) so an incompatible value is dropped rather
than crashing. The exact-match and list/set branches need no change (they are
already safe).

`test_search_filter_lte_type_mismatch_does_not_crash`) that assert the
CORRECTED contract (no TypeError; the str item value is dropped, the numeric
item is kept). They XFAIL on current main (proving the defect); they will
XPASS->RED on the fix branch until the implementer guards the comparison, at
which point the validator flips them to hard passes and closes this ticket.
The same file armor-pins the SAFE branches the module already delivers
correctly (exact-match type mismatch, list/set type mismatch, homogeneous
numeric `$gte`, and the documented `None`-value skip) so a future refactor
that unifies the branches into a single comparison cannot regress them.
