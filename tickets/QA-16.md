# QA-16: negative-slice "top N" leak — content_search.SearchIndex.search(limit=-1)

## Symptom
The negative-slice "top N / limit" defect class (QA-1 `extract_top_n`, QA-2
`tfidf`/`index.search`, QA-3 `Feed.get_recent_entries`, QA-4 sweep of 13 sites,
QA-5 sweep of 9 sites, QA-15 `content_summarizer.summarize` — all now CLOSED
except QA-15) has a **NEW public site missed by QA-4's sweep table**:
`content_search.SearchIndex.search(query, limit=-1)`.

QA-4's sweep table listed `content_search.py SearchIndex.get_suggestions(limit)`
(line ~483) as a site but **omitted `content_search.py SearchIndex.search(limit)`**
(line 334) — the same "site missed by the sweep" gap that let QA-15 slip past
QA-5's 9-site sweep.

`SearchIndex.search` does `page = ranked[offset:offset + limit]` with no
negative guard on `limit`. A negative `limit` leaks Python negative-slice
semantics: `ranked[offset:offset-1]` returns **all-but-last** ranked entries
instead of an empty list. The `0` bound is correct (returns `[]`); the negative
bound is not.

Out-of-range (negative) N must yield an empty list, matching the zero guard —
the same contract QA-1..QA-5/QA-15 established and the implementer has already
applied at every other public "top N" site.

## Affected site (1, confirmed leaking at HEAD)
| module | function | line | idiom |
|--------|----------|------|-------|
| content_search.py | `SearchIndex.search` | 334 | `ranked[offset:offset + limit]` |

Reachable through the public entry point
`PersonalIndexApp.search(query, limit=-1)` -> `ContentSearch.search` ->
`SearchIndex.search` (the `app.search` docstring documents `limit` as a
pass-through with no negative guard).

A whole-codebase re-sweep of the slicing idiom
(`grep -rnE '\[:[a-z_]+\]' personal_index/`) confirms **content_search.SearchIndex.search
is the only public "top N" site still leaking** — every other site (rss,
progress, content_annotations, content_collections, content_scoring,
search_index, content_recommender, search_suggestions, content_linker,
tfidf, keyword_extractor, content_categorizer, content_digest, cli, cli_top,
formatter, content_export_csv, text_utils, export_markdown, filter/engine,
content_search.get_suggestions, index, dashboard/aggregator) is now guarded
with `if <bound> <= 0: return []` (or an equivalent `> 0` ternary / `max(0, ...)`
clamp). The dashboard/aggregator negative-limit paths are private helpers only
ever called with their positive defaults, so they are not a public leak.

## Exact repro
    python3 -c "
    from personal_index.content_search import SearchIndex
    idx = SearchIndex()
    for u in 'abc':
        idx.add_item({'id': u, 'url': u, 'title': u + ' guide',
                      'content': ('the guide to programming languages and their design ' * 4) + u})
    r = idx.search('guide', limit=-1)
    print('limit=-1 -> total', r['total'], 'len(results)', len(r['results']),
          [e['item']['id'] for e in r['results']])
    r0 = idx.search('guide', limit=0)
    print('limit=0  -> total', r0['total'], 'len(results)', len(r0['results']))
    "

## Observed
    limit=-1 -> total 3 len(results) 2 ['c', 'b']
    limit=0  -> total 3 len(results) 0

## Expected (per the QA-1..QA-5/QA-15 contract)
    limit=-1 -> total 3 len(results) 0 []
    limit=0  -> total 3 len(results) 0 []

`limit=-1` must return `{"results": [], "total": 3, "query": "guide"}` —
exactly as `limit=0` already does.
