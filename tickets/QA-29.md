# QA-29: `split_by_size` measures CHARACTERS, not BYTES — a multi-byte chunk can exceed `max_bytes`

- Status: IMPLEMENTED #1293@85c2e53
- Kind: QA
- Component: `personal_index/sitemap_builder.py` (`SitemapBuilder.split_by_size`)
- Contract home: ARCH-22 (issue #1060) — the byte-limit enforcement the
  implementer added in Option A. This ticket covers a gap in that enforcement
  path, NOT the namespace defect (QA-23, #1228) and NOT the dead-constant
  issue (ARCH-22, now VERIFIED).
- Issue: #1251
- Deep test: `tests/deep/test_sitemap_split_by_size_adversarial.py::TestQA29ByteVsCharacter`
  (2 xfail-strict defect pins; flip to hard passes on fix)

## Symptom

`SitemapBuilder.split_by_size(max_bytes=...)` is documented to break a chunk
when adding the next entry would push the chunk past `max_bytes`, and to
guarantee that "a chunk returned here serializes to **at most max_bytes
bytes** when passed to `build()`" (docstring, and
`docs/content-sitemap.md` Public API + contract-hole-1 RESOLVED note).

But the per-entry measurement is:

    entry_bytes = len(tostring(entry.to_element(), encoding="unicode"))

`tostring(..., encoding="unicode")` returns a `str`, so `len(...)` is a
**character** count, not a byte count. For ASCII content characters == bytes
and the guarantee holds. For multi-byte (non-ASCII) content the UTF-8 byte
length exceeds the character length, so the running total under-counts and a
returned chunk serializes to **more** than `max_bytes` bytes.

## Repro (exact command)

    python3 -c "
    from personal_index.sitemap_builder import SitemapBuilder
    b = SitemapBuilder()
    for i in range(10):
        b.add_entry('http://example.com/' + '\u00e9'*1000)   # ~1000 chars, ~3000 UTF-8 bytes each
    for i, chunk in enumerate(b.split_by_size(max_bytes=5000)):
        bb = SitemapBuilder(); bb.add_entries(chunk)
        print(f'chunk {i}: {len(chunk)} entries -> {len(bb.build())} bytes (limit 5000)')
    "

## Observed output

    chunk 0: 3 entries -> 6524 bytes (limit 5000)
    chunk 1: 3 entries -> 6524 bytes (limit 5000)
    chunk 2: 3 entries -> 6524 bytes (limit 5000)
    chunk 3: 1 entries -> 2252 bytes (limit 5000)

Chunks 0-2 each serialize to **6524 bytes**, exceeding the 5000-byte budget
the caller requested. The same builder with ASCII URLs of identical character
length stays under the limit — confirming the gap is the character-vs-byte
measurement, not the chunking logic.

## Expected per docs

`docs/content-sitemap.md` (Public API — `split_by_size`): "a chunk returned
here serializes to **at most max_bytes bytes** when passed to `build()`".
`SitemapBuilder.split_by_size` docstring: "breaks a chunk when adding the next
entry would push the chunk's serialized size past `max_bytes` ... so a chunk
returned here serializes to at most `max_bytes` bytes when passed to
`build()`".

For the guarantee to hold, the per-entry measurement must be the UTF-8 byte
length, e.g. `len(tostring(entry.to_element(), encoding="unicode").encode("utf-8"))`
(or `tostring(..., encoding="utf-8")`), and the fixed wrapper overhead must be
measured the same way.

## Note on the architect's spec

ARCH-22's Option-A spec itself suggested `len(tostring(entry.to_element(),
encoding="unicode"))` as the measurement. That is a character count, so the
spec's own suggested measurement does not satisfy the "at most max_bytes
bytes" contract for non-ASCII content. The fix is to measure UTF-8 bytes.
