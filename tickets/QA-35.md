# QA-35: search_suggestions.suggest(fuzzy=True) leaks all-but-last on negative max_suggestions

## Symptom
SearchSuggestions.suggest(prefix, fuzzy=True) caps its result with
sorted_suggestions[: self.max_suggestions] (personal_index/search_suggestions.py:206)
with NO max_suggestions <= 0 guard. When max_suggestions is negative,
the slice is [:-1] (all-but-last) instead of [].

SearchSuggestions(max_suggestions=-1, fuzzy_threshold=0.0) with 5 history
entries sharing the py prefix returns 4 suggestions (all-but-last) from
suggest('py', fuzzy=True) instead of 0.

## Why it is a real contract violation
- The sibling methods in the SAME class DO guard: get_trending(n) and
  get_related_queries(query, n) both have an explicit if n <= 0: return []
  before their [:n] slice. suggest is the only public top-N method in the
  class without the guard.
- The suggest docstring says it "Returns the top max_suggestions by score
  descending." A negative max_suggestions is out-of-range and must yield an
  empty result, consistent with the 0 guard and the sibling methods.
- This is the same defect class as QA-4/5/27/28 (the negative-slice "top N"
  leak, ARCH-17 issue #1049). The prior sweeps (QA-4's table) listed
  search_suggestions.get_trending and get_related_queries but NOT suggest —
  the exact-match path is accidentally masked by Counter.most_common(-1) ->
  [], so the sweep's negative-N probe of the exact-match path returned [] and
  the site was marked guarded. The leak is only reachable through the fuzzy
  path, which adds candidates directly to the candidates dict (not via
  most_common), so the final [: self.max_suggestions] slice is the only cap
  and it leaks.

## Exact repro
    from personal_index.search_suggestions import SearchSuggestions
    s = SearchSuggestions(max_suggestions=-1, fuzzy_threshold=0.0)
    s.add_search_history(['python','pytorch','pandas','pypi','pyramid'])
    print([x.text for x in s.suggest('py', fuzzy=True)])
Actual: ['python', 'pytorch', 'pypi', 'pyramid'] (4 items, all-but-last)
Expected: [] (0 items)

## Traceback / evidence
No exception is raised — the leak is a silent partial result. The failing
assertion (from the deep test) is:
    assert _fuzzy_suggestions(-1) == []
    E   AssertionError: assert ['python', 'pytorch', 'pypi', 'pyramid'] == []
The exact-match path (no fuzzy) returns [] for max_suggestions=-1, but for
the wrong reason (Counter.most_common(-1) -> []), so it does not exercise the
leak.

## Expected per docs
docs/search-suggestions.md documents suggest as returning "the top
max_suggestions by score descending" and documents the 0/short-prefix guard
(if len(prefix) < min_prefix_length, returns []). The sibling methods
get_trending/get_related_queries are documented with explicit n <= 0 -> []
guards. A negative max_suggestions is out-of-range and must yield [],
consistent with the 0 guard.

## Fix (implementer)
Add a guard in SearchSuggestions.suggest before the final slice (line 206):
    if self.max_suggestions <= 0:
        return []
(or clamp the slice to [: max(0, self.max_suggestions)]). This makes the
xfail-strict pins in tests/deep/test_negslice_sweep4_adversarial.py XPASS,
which turns them red (xfail-strict) — the signal to re-verify and close QA-35.

## Deep test
tests/deep/test_negslice_sweep4_adversarial.py
- TestSuggestFuzzyNegativeMaxSuggestions (3 pins, xfail-strict): documents the
  leak; XPASSes (-> red) once the guard is added.
- TestSuggestFuzzyArmor (6 pins, clean): the 0 guard, positive caps, the
  accidentally-masked exact-match path, and the already-guarded sibling methods.
