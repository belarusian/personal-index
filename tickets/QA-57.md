# QA-57: `PermissionChecker.__init__` shallow-copies `ROLE_PERMISSIONS`, so `add_role_permissions` on one instance mutates the module-level constant and leaks into every other instance

**Status:** CLOSED (validator cycle 333 @ main 54e8cc3; fix #1707@4ed3eb99 verified: pinning test test_add_role_permissions_is_instance_isolated passes + adversarial repro confirms fresh instance isolated, global ROLE_PERMISSIONS unpolluted, check/check_any/check_all consult instance map)
**Issue:** #1687
**Deep test:** tests/deep/test_auth_adversarial.py::TestPermissionCheckerAdversarial::test_add_role_permissions_is_instance_isolated (xfail-strict, pins this defect)

## Symptom

`PermissionChecker.add_role_permissions(role, permissions)` is documented as an
instance-level customization ("Add custom permissions to a role"), and
`get_role_permissions` returns a `.copy()`, implying per-instance isolation.
But customizing ONE `PermissionChecker` instance permanently mutates the
module-level `ROLE_PERMISSIONS` constant, so EVERY other `PermissionChecker`
instance in the process (and any code reading `ROLE_PERMISSIONS` directly)
sees the change. This is a cross-instance / cross-module state leak in a
security-relevant permission system.

    >>> from personal_index.auth.permissions import (
    ...     PermissionChecker, Role, Permission, User, ROLE_PERMISSIONS)
    >>> a = PermissionChecker()
    >>> a.add_role_permissions(Role.CRAWLER, {Permission.WRITE_INDEX})
    >>> b = PermissionChecker()                      # fresh, independent instance
    >>> u = User(user_id="u", username="c", roles=[Role.CRAWLER])
    >>> b.check(u, Permission.WRITE_INDEX)
    True        # DEFECT: b was never customized, yet it grants WRITE_INDEX
    >>> Permission.WRITE_INDEX in ROLE_PERMISSIONS[Role.CRAWLER]
    True        # DEFECT: the module-level constant was mutated

## Root Cause

`personal_index/auth/permissions.py:77`:

    self._role_permissions = custom_role_permissions or ROLE_PERMISSIONS.copy()

`dict.copy()` is a SHALLOW copy: the new dict has its own keys but the values
(the `set[Permission]` objects) are the SAME objects as in the module-level
`ROLE_PERMISSIONS`. `add_role_permissions` then does
`self._role_permissions[role].update(permissions)`, which mutates the shared
set in place — i.e. it mutates `ROLE_PERMISSIONS[role]` itself.

## Expected (per docs/contract)

- `add_role_permissions` is per-instance: customizing one `PermissionChecker`
  must not affect another instance or the module-level `ROLE_PERMISSIONS`.
- The fix is a deep copy at construction, e.g.
  `self._role_permissions = {r: set(p) for r, p in ROLE_PERMISSIONS.items()}`
  (or `copy.deepcopy(ROLE_PERMISSIONS)`), so each instance owns its own sets.

## Notes

- Security-relevant: a stray customization (or a test that calls
  `add_role_permissions`) silently widens permissions for every other checker
  in the process.
- The deep test is pinned xfail-strict so it turns main RED the moment the
  implementer lands the deep-copy fix (the assertion then passes and the
  strict xfail fails) — at which point the validator flips it to a plain
  assertion and closes this ticket.
