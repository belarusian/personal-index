# QA-34: cycle_signals.format_tree ignores its documented `max_lines` hard cap

- **Status:** OPEN
- **Kind:** QA
- **Module:** `personal_index/cycle_signals.py` (`format_tree`, CLI `--lines`)
- **Issue:** #1265
- **Deep test:** `tests/deep/test_cycle_signals_adversarial.py::test_format_tree_max_lines_is_a_hard_cap`
- **Discovered:** cycle 205 (validator)

## Symptom

`format_tree(tree, max_depth=2, max_lines=50)` documents `max_lines` as a
**"hard cap on output lines"** (line 280), and the CLI exposes the same
parameter as `--lines` with help text **"Max output lines for tree
(default: 50)"** (line 676), passed straight through at line 694.

But the code never truncates the output to `max_lines`. The only use of
`max_lines` in the function is the gate at line 294:

    if clean and len(lines) < max_lines - 3:

which decides *whether to render the clean (unflagged) packages* — it is not
a cap. The flagged-package loop above it (line 290, `for name, node in
flagged: _render_summary_node(...)`) appends one line per flagged package
with no bound, so the output length is driven entirely by the number of
flagged packages, not by `max_lines`.

With 30 flagged packages the output is **90 lines** for `max_lines=10`,
`max_lines=5`, and even `max_lines=1` alike. The documented hard cap is
never enforced.

## Exact repro

Run (python3):

    from personal_index.cycle_signals import build_tree, format_tree
    mods = []
    for i in range(30):
        for j in range(2):
            mods.append({"name": f"pkg{i:02d}.mod{j}", "lines": 50,
                         "functions": 5, "classes": 0, "tests": 0,
                         "ruff_errors": 1, "mypy_errors": 0,
                         "ruff_warnings": 0, "imports": []})
    tree = build_tree(mods)
    for ml in (10, 5, 1):
        out = format_tree(tree, max_depth=2, max_lines=ml)
        print(ml, len(out.splitlines()))

## Observed output

    10 90
    5 90
    1 90

End-to-end CLI (same codemap, `--format tree`):

    python3 -m personal_index.cycle_signals codemap.json --format tree --lines 5
    # -> 90 lines on stdout (cap of 5 not applied)

## Expected per docs/docstrings

`format_tree` must honor its documented contract: the returned string must
contain **at most `max_lines` lines** (a hard cap). The CLI `--lines` flag
("Max output lines for tree") must therefore bound the tree output to that
many lines. A natural fix is to truncate `lines` to `max_lines` before
joining (e.g. `return "\n".join(lines[:max_lines])`), or to stop appending
once `len(lines) >= max_lines`.

## Minimal additive fix (for implementer)

In `format_tree`, enforce the cap before returning, e.g.:

    return "\n".join(lines[:max_lines])

(or stop appending once `len(lines) >= max_lines`). This makes the
documented "hard cap on output lines" true and makes the CLI `--lines`
flag bound the output as its help text promises.

## Notes

- cycle_signals is a never-probed module with NO docs page; the defect is a
  docstring/CLI-help contract the code does not deliver (the "hard cap"
  claim), not a documented design constraint.
- The `max_lines - 3` gate at line 294 is a separate (clean-package
  rendering) concern and is not the cap; it should remain, with a real cap
  added on top.
